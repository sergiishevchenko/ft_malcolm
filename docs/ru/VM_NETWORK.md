## 1. Короткий ответ

Две виртуальные машины стоят в одной сети друг с другом. Mac стоит в других.

| Машина | Где смотреть | IP | Сеть |
|--------|----------------|----|------|
| Mac, обычный выход в интернет | `en0` | `192.168.1.5` | домашняя `192.168.1.0/24` |
| Mac, другой виртуальный свитч | `bridge100` | `192.168.64.1` | `192.168.64.0/24` |
| Атакующий | `enp0s1` | `192.168.65.14` | `192.168.65.0/24` |
| Цель | `enp0s1` | `192.168.65.15` | `192.168.65.0/24` |

Маска у всех этих адресов — `/24`, то есть `255.255.255.0`. Соседями считаются только те, у кого совпадают первые три числа. `192.168.65.14` и `192.168.65.15` совпадают. `192.168.64.1` и `192.168.1.5` — уже другие сети.

Сеть `192.168.65.0/24` на этом Mac создаёт Docker Desktop для своей служебной Linux-машины, не для виртуалок проекта. Номер `.65` стоит рядом с сетью Apple `192.168.64.0/24` на `bridge100`, чтобы они не пересеклись. Шлюз внутри — `192.168.65.1`, его держит vpnkit, а не карта Mac, поэтому `ifconfig` этот адрес не показывает. Подробнее в разделе 8.

## 2. Три сети на одном Mac

Один компьютер может быть в нескольких сетях сразу. У каждой свой интерфейс и свой IP.

### Домашняя сеть

`en0` — Wi-Fi или кабель Mac. Адрес `192.168.1.5`. Через него Mac ходит в интернет и видит домашний роутер. Виртуалки проекта к этому проводу не подключены.

### Мост 192.168.64.0/24

`bridge100` — виртуальный свитч самой macOS. На нём адрес `192.168.64.1`, MAC `be:d0:74:a4:60:64`. В мост включён порт `vmenet0` (виртуальная карта). Это отдельный свитч для других виртуальных машин. Атакующий и цель к нему не подключены: у них третье число `65`, не `64`.

### Сеть проекта 192.168.65.0/24

Здесь живут обе машины ft_malcolm:

| | Атакующий | Цель |
|--|-----------|------|
| Имя в системе | `attacker-QEMU-Virtual-Machine` | своя виртуалка |
| Интерфейс | `enp0s1` | `enp0s1` |
| IP | `192.168.65.14/24` | `192.168.65.15/24` |
| MAC | `aa:77:fb:2e:e0:ed` | `aa:77:fb:2e:e0:aa` |
| Как получен IP | DHCP (`dynamic` в `ip addr`) | DHCP |

Они видят кадры Ethernet друг друга напрямую. Именно поэтому ARP-запрос с цели доходит до атакующего, и ft_malcolm может на него ответить.

```
домашняя сеть                другой виртуальный свитч         сеть проекта
192.168.1.0/24               192.168.64.0/24                  192.168.65.0/24

Mac en0                      Mac bridge100                    атакующий  .14
192.168.1.5                  192.168.64.1                     цель       .15
                                                              шлюз       .1
                                                              VM Docker
```

Стрелок между колонками нет: это не один свитч, разрезанный на части. Это три разных сегмента. Кадр с `enp0s1` цели не появляется на `en0` и не появляется на `bridge100`.

## 3. Что такое кадр

По проводу и по виртуальному свитчу едет не «IP-адрес» и не «ping». Едет **кадр**: короткая посылка с адресом получателя, адресом отправителя и содержимым.

Карту не интересует, ping это или ARP. Она смотрит только на начало кадра. Это заголовок Ethernet, 14 байт:

| Поле | Длина | На что похоже | Пример |
|------|-------|----------------|--------|
| MAC получателя | 6 байт | на какой карте остановиться | `aa:77:fb:2e:e0:aa` |
| MAC отправителя | 6 байт | кто отправил | `aa:77:fb:2e:e0:ed` |
| тип | 2 байта | что лежит внутри | `0x0806` — это ARP, `0x0800` — это обычный IP |

Дальше идёт содержимое. У ARP в этом проекте оно занимает 28 байт. Вместе с заголовком выходит 42 байта. Именно такой кадр собирает ft_malcolm.

Внутри ARP снова есть адреса, но уже другие: IP и MAC того, про кого спрашивают. Это не адрес на конверте. Конверт — внешние MAC. Записка внутри — «кто имеет `192.168.65.14`?».

Три частых адреса получателя:

| MAC получателя | Кому кадр | Пример |
|----------------|-----------|--------|
| MAC одной карты | только ей | ответ ft_malcolm на `aa:77:fb:2e:e0:aa` |
| `ff:ff:ff:ff:ff:ff` | всем на этом свитче | ARP-вопрос «кто имеет этот IP?» |
| `de:ad:be:ef:00:01` | никому: такой карты в сети нет | куда цель шлёт пакеты после подмены |

## 4. Как кадр передаётся

Путь одного вопроса «кто имеет `192.168.65.14`?» с цели на атакующего:

1. Программа на цели (`arping` или `ping`) просит ядро узнать MAC для `192.168.65.14`.
2. Ядро цели собирает кадр. Получатель — `ff:ff:ff:ff:ff:ff`, отправитель — `aa:77:fb:2e:e0:aa`. Внутри написано: спрашиваю `192.168.65.14`, мой IP `192.168.65.15`.
3. Карта `enp0s1` цели отдаёт кадр в свой порт виртуального свитча. Провода нет: порт — это связь между программой-свитчем и этой виртуалкой.
4. Свитч видит `ff:ff:ff:ff:ff:ff` и копирует кадр во все остальные свои порты.
5. Карта атакующего `enp0s1` получает копию. MAC получателя — «всем», поэтому карта кадр не выбрасывает.
6. ft_malcolm читает кадр, узнаёт в нём нужный вопрос и собирает ответ. Получатель ответа — уже не «всем», а `aa:77:fb:2e:e0:aa`. Отправитель в заголовке — `de:ad:be:ef:00:01`.
7. Свитч смотрит этот MAC получателя. Он уже видел, что `aa:77:fb:2e:e0:aa` живёт на порту цели, и отдаёт кадр только туда.
8. Карта цели принимает кадр, потому что MAC получателя совпал с её собственным. Ядро читает записку: «`192.168.65.14` находится по `de:ad:be:ef:00:01`» и записывает это в таблицу.

Дальше обычный ping идёт тем же путём, только внутри кадра уже IP-пакет, а MAC получателя — тот, что лежит в таблице. После подмены это `de:ad:be:ef:00:01`. Свитч ищет порт с таким MAC, не находит и кадр ни на атакующего, ни на цель не попадает.

На каждой границе свитча конверт меняется. Домашний роутер, получив кадр из одной сети, снимает Ethernet и собирает новый кадр уже для следующей сети. Поэтому MAC цели бессмысленен в сети `192.168.1.0/24`: там другие карты и другой свитч.

## 5. Что такое сетевая карта

**Сетевая карта** — устройство, которое стоит между системой и свитчем. Программы и ядро отдают ей готовый кадр. Она выкладывает его в свой порт. Чужой кадр, пришедший с порта, она либо поднимает в ядро, либо выбрасывает.

В виртуалке отдельной платы нет. Карту рисует гипервизор, для гостя она выглядит настоящей. У атакующего и у цели она называется `enp0s1`. У Mac настоящая карта выхода в дом называется `en0`: это Wi-Fi или кабель. `bridge100` картой не является, это свитч.

У каждой карты один MAC. Его ядро показывает в строке `link/ether`:

| Карта | Где | MAC |
|-------|-----|-----|
| `enp0s1` атакующего | виртуалка | `aa:77:fb:2e:e0:ed` |
| `enp0s1` цели | виртуалка | `aa:77:fb:2e:e0:aa` |
| `en0` | Mac | адрес домашнего Wi-Fi или кабеля |

IP на карте может быть один, несколько или ни одного. MAC при этом один. `192.168.65.14` висит на `enp0s1` атакующего, но кадр адресуется не этим IP, а MAC.

Имя `enp0s1` ядро собрало само: карта сидит на шине PCI, слот 0, функция 1. В старых системах такую же карту часто звали `eth0`. Для программы важно имя, которое видно в `ip link`, и его индекс. Индекс ft_malcolm потом указывает в отправке, чтобы кадр вышел именно из этой карты.

Карта считается рабочей, когда она включена и на ней есть связь со свитчем. В `ip addr` это флаги `UP` и `LOWER_UP`. `UP` значит «система разрешила карте работать». `LOWER_UP` значит «с той стороны кто-то отвечает», здесь это виртуальный свитч, не лампочка на кабеле.

### Что карта делает при отправке

1. Ядро или ft_malcolm кладёт в карту кадр: MAC получателя, MAC отправителя, тип и содержимое.
2. Карта не выбирает, кому нести кадр дальше. Она отдаёт его в тот единственный порт, к которому подключена.
3. Дальше решает свитч.

ft_malcolm как раз обходит обычную отправку IP. Он сам заполняет 42 байта и просит ядро выложить их в `enp0s1`. Карта не проверяет, правда ли в кадре написано «я владелец `192.168.65.14`».

### Что карта делает при приёме

Кадр уже пришёл на порт. Карта смотрит только MAC получателя в начале:

| MAC получателя | Решение карты |
|----------------|----------------|
| совпал с её собственным | отдать кадр ядру |
| `ff:ff:ff:ff:ff:ff` | отдать ядру: это «всем» |
| чужой одиночный MAC | выбросить, до программ он не доходит |

Поэтому ответ ft_malcolm с получателем `aa:77:fb:2e:e0:aa` поднимает только карта цели. Карта атакующего тот же кадр отбрасывает: в заголовке не её MAC и не «всем».

Кадр на `de:ad:be:ef:00:01` не принимает ни одна карта в сети. Даже если свитч скопирует его на все порты, каждая карта сверит MAC получателя со своим и выбросит его. Ядро атакующего этот трафик не увидит, пока карту специально не переведут в режим «принимать всё». ft_malcolm этот режим не включает: ему нужен только широковещательный ARP-вопрос.

Подробный разбор полей и байтов кадра: [NIC.md](NIC.md).

## 6. Что такое свитч

**Свитч** (его же называют коммутатором; «свитчер» — то же самое) — устройство с несколькими портами. В каждый порт воткнут один кабель или одна виртуальная машина. Задача свитча: принять кадр с одного порта и отдать его на тот порт, где сидит нужная карта.

Домашний пример — коробочка с лампочками, в которую воткнуты компьютер, приставка и роутер. В этой лаборатории коробочка программная:

| Свитч | Порты | Кто подключён |
|-------|--------|----------------|
| сеть проекта, `192.168.65.0/24` | виртуальные | атакующий, цель, шлюз vpnkit, служебная VM Docker |
| `bridge100`, `192.168.64.0/24` | `vmenet0` и адрес самого Mac | другие виртуалки, не эти две |
| домашний роутер | кабели и Wi-Fi | Mac через `en0`, телефон, остальные устройства дома |

У `bridge100` это видно в `ifconfig`: строка `member: vmenet0` и есть порт. Сеть `.65` устроена так же, только её порты не показаны в `ifconfig` Mac, потому что свитч живёт у Docker.

Свитч не понимает IP. Числа `192.168.65.14` и `192.168.65.15` для него не существуют. Он читает только MAC в начале кадра. Решение «эти двое в одной IP-сети» принимает уже ядро каждой виртуалки, когда выбирает, слать кадр соседу напрямую или на шлюз.

Свитч — не хаб. Хаб тупо копирует каждый кадр на все порты. Свитч запоминает, какая карта за каким портом, и одиночный кадр несёт только туда.

## 7. Как свитч выбирает порт

Память свитча — таблица «MAC → порт». Сначала она пустая. Она наполняется сама, без настройки.

Пришёл кадр на порт цели, MAC отправителя `aa:77:fb:2e:e0:aa`. Свитч записывает: эта карта за портом цели. Пришёл кадр с атакующего, отправитель `aa:77:fb:2e:e0:ed`. Появляется вторая строка. Чужой MAC в таблице не создаётся, пока с этой карты не придёт хотя бы один кадр.

Дальше свитч смотрит MAC получателя:

| Кому адресован кадр | Что делает свитч |
|---------------------|------------------|
| MAC есть в таблице | отдаёт только на записанный порт |
| MAC в таблице нет | копирует на все порты, кроме входящего: вдруг карта там и ответит |
| `ff:ff:ff:ff:ff:ff` | всегда копирует на все остальные порты |

Отсюда поведение ft_malcolm в этой сети.

ARP-вопрос с цели адресован `ff:ff:ff:ff:ff:ff`. Свитч рассылает его на все свои порты. Атакующий его видит. Если бы атакующий был на `bridge100`, порта в этом свитче у него бы не было, и вопрос до него не дошёл.

Ответ ft_malcolm адресован `aa:77:fb:2e:e0:aa`. Этот MAC свитч уже видел на порту цели, поэтому ответ уходит только цели. Служебная машина Docker и шлюз этот ответ не получают.

Позже цель шлёт обычные кадры на `de:ad:be:ef:00:01`. Такой строки в таблице нет: ни одна карта с этим MAC кадры не отправляла. Свитчу некуда их доставить. Атакующий их тоже не получает: в заголовке стоит не его MAC `aa:77:fb:2e:e0:ed`.

Запись в таблице живёт не вечно. Если карта замолчала, свитч её забывает. Следующий кадр на этот MAC снова уйдёт на все порты, пока карта сама что-нибудь не пошлёт и не напомнит, где она.

Один свитч не соединяет разные сети сам. `bridge100` не переносит кадр в сеть `.65`. Для этого нужен роутер: он принимает кадр, смотрит IP внутри и собирает новый кадр уже в другой сети. В лаборатории так делает шлюз `192.168.65.1`, когда виртуалка открывает сайт в интернете. На ARP между `.14` и `.15` он не нужен: обе карты и так на одном свитче.

## 8. Кто создал сеть виртуалок

Её не создавала команда в терминале и не домашняя сеть. Её поднимает **Docker Desktop**, он на этом Mac запущен.

Docker не ставит контейнеры прямо на macOS. Он запускает одну служебную Linux-машину через Apple Virtualization. У процесса такое имя:

```
com.docker.virtualization
```

В параметрах её ядра есть `eth0.dhcp`, `eth1.dhcp` и `vpnkit.connect`. Смысл простой:

1. Гостевая Linux получает сетевые карты.
2. Адрес ей выдаёт DHCP, не статическая настройка.
3. За DHCP, DNS и выход в интернет отвечает **vpnkit** — программа Docker на стороне Mac. Она сидит между гостем и настоящими сетями Mac.

Пул адресов этой схемы — `192.168.65.0/24`. В настройках Docker Desktop это поле **Docker subnet**, и такое значение стоит по умолчанию. Сеть нужна служебной Linux-машине Docker: интернет, DNS и прокси. Для двух виртуалок проекта её не создавали.

Номер `.65` выбран рядом с сетью Apple. Общий свитч виртуалок macOS — это `bridge100` и `192.168.64.0/24`. Там Mac сам стоит на `192.168.64.1`, адрес виден в `ifconfig`. Docker берёт следующую сеть `/24`, чтобы с этим свитчем не пересечься. Шлюз `.1` при этом остаётся внутри vpnkit, отдельной карты Mac в `192.168.65.0/24` нет, поэтому `ifconfig | grep "inet 192.168.65"` пустой.

Атакующий и цель попали сюда уже потом. DHCP того же пула выдал им `192.168.65.14` и `192.168.65.15`: в `ip addr` у обеих написано `dynamic`.

Шлюз по умолчанию внутри этой сети — `192.168.65.1`. Его держит vpnkit. Через него виртуалка выходит в интернет: пакет уходит на `.1`, vpnkit выпускает его наружу уже от Mac.

## 9. Кто в ней есть

Сеть маленькая. Кроме двух машин проекта в ней обычно ещё служебные узлы Docker.

| Адрес | Кто это | Зачем |
|-------|---------|--------|
| `192.168.65.1` | шлюз vpnkit | DHCP, DNS, выход в интернет. На Mac в `ifconfig` этого адреса нет |
| `192.168.65.14` | атакующий | здесь запускается `ft_malcolm` |
| `192.168.65.15` | цель | сюда уходит поддельный ARP-ответ |
| адрес по DHCP | служебная Linux-машина Docker | на ней живут контейнеры Docker, это не атакующий и не цель |
| `192.168.65.255` | broadcast | «всем в этой сети». Сюда уходит ARP-запрос |
| `192.168.65.0` | номер сети | на карту его не назначают |

Контейнеры Docker (адреса вида `172.17.0.0/16`) в этот список не входят. Они находятся внутри служебной Linux-машины, за ещё одним мостом. До `enp0s1` атакующего их кадры сами не доходят.

Домашние устройства из `192.168.1.0/24` здесь тоже не появляются. Mac их видит через `en0`, виртуалки — нет.

Узнать живых соседей можно только с виртуалки: Mac в этой сети не состоит, его `arp` про `192.168.65` пустой.

```bash
ip route | grep default
ping -c 1 192.168.65.1
ip neigh
```

`default via` показывает шлюз. После `ping` в `ip neigh` появится его MAC. Строки `.14` и `.15` — две машины проекта. Остальные ответы — служебные узлы той же сети.

## 10. Почему Mac её не видит

На Linux список адресов печатает `ip addr show`. На Mac этой команды нет. Там то же самое делает `ifconfig`.

Проверка, есть ли у Mac адрес в сети проекта:

```bash
ifconfig | grep "inet 192.168.65"
```

Пустой вывод значит: ни на одной карте Mac нет `192.168.65.x`. Так и задумано у vpnkit. Шлюз `.1` существует только для гостей. Снаружи, в списке интерфейсов macOS, его нет.

Поэтому картина такая:

- с атакующего цель пингуется, ARP между ними проходит;
- с Mac адрес `192.168.65.14` не является соседом по своей карте;
- `bridge100` с адресом `192.168.64.1` выглядит похоже, но это другой свитч. Третье число другое, кадры туда не попадают.

---

## 11. Как это относится к ft_malcolm

Программе нужен один L2-сегмент: цель шлёт широковещательный ARP, атакующий его слышит. Этот сегмент — `192.168.65.0/24` между двумя виртуалками. Mac для этого не нужен.

Практические следствия:

- Проверять таблицу ARP надо на цели (`192.168.65.15`), не на Mac.
- `tcpdump` для кадров программы запускают на `enp0s1` виртуалки, не на `en0` и не на `bridge100`.
- `source_ip` в команде — `192.168.65.14`, собственный адрес атакующего. Его ядро тоже отвечает на ARP и называет MAC `aa:77:fb:2e:e0:ed`. Поддельный MAC — `de:ad:be:ef:00:01`.
- Выход виртуалки в интернет через `192.168.65.1` на работу ft_malcolm не влияет. Программа эти пакеты не смотрит: сокет принимает только ARP.

## 12. Как проверить

### На Mac

```bash
# своих адресов в сети проекта нет — команда ничего не печатает
ifconfig | grep "inet 192.168.65"

# адрес в домашней сети
ifconfig en0 | grep "inet "

# другой виртуальный свитч, не сеть проекта
ifconfig bridge100 | grep "inet "
```

### На виртуалке

```bash
# свой IP и MAC
ip addr show enp0s1

# шлюз сети 192.168.65.0/24
ip route | grep default

# кто ответил на ARP
ping -c 1 192.168.65.1
ip neigh
```

Ожидание на атакующем: `inet 192.168.65.14/24` и `link/ether aa:77:fb:2e:e0:ed`. На цели: `192.168.65.15` и `aa:77:fb:2e:e0:aa`. Шлюз в `ip route` — `192.168.65.1`.

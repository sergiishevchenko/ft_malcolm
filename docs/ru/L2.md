# Сеть L2

Канальный уровень: сегмент, в котором кадр Ethernet доходит от одной сетевой карты до другой без роутера. Здесь живут MAC, свитч, broadcast и ARP. За границей этого сегмента ft_malcolm не работает.

## 1. Что такое L2

**L2** — второй уровень модели OSI, Data Link. Его задача: доставить кадр соседнему интерфейсу по общей среде. Сосед — тот, кто подключён к тому же коммутатору, мосту, VLAN или точке доступа. Не «тот, у кого есть IP в интернете».

На Ethernet L2 адресует кадр по **MAC**. IP на этом уровне не читают. Свитч не знает, что внутри кадра `192.168.65.15` или `8.8.8.8`. Он смотрит destination MAC и решает, в какой порт отправить.

Имена одного и того же куска сети:

| Слово | Что имеют в виду |
|-------|------------------|
| L2-сегмент | хосты, которые видят кадры друг друга без роутера |
| broadcast domain | кто получит кадр на `ff:ff:ff:ff:ff:ff` |
| VLAN | один такой домен, нарезанный на коммутаторе |
| LAN | обычно вся локалка за домашним роутером; внутри неё L2 один, если нет VLAN |
| link / «линк» | конкретный кабель или виртуальный провод до ближайшего моста |

Две VM в разных NAT-сетях могут пинговать `1.1.1.1` и при этом **не** быть в одном L2. Ping в интернет доказывает маршрут, не общий сегмент.

## 2. Место в стеке

```
L7   приложение          curl, ping
L4   транспорт           TCP, UDP, порты
L3   сеть                IPv4, маршрутизация, TTL
L2   канал               Ethernet, MAC, свитч, ARP как сосед L2/L3
L1   физика              кабель, радио, биты
```

ARP формально сидит между L2 и L3: едет в Ethernet-кадре (EtherType `0x0806`), а смысл у него про IP. Широковещательный ARP Request не пересекает роутер, потому что роутер — граница L2.

Что L2 делает и чего не делает:

| Делает | Не делает |
|--------|-----------|
| доставляет кадр по MAC в сегменте | не выбирает путь через интернет |
| учит, какой MAC за каким портом | не уменьшает TTL |
| размножает broadcast на все порты VLAN | не смотрит на TCP-порт |
| отбрасывает кадр с чужим dest, если порт уже выучен | не проверяет, врёт ли ARP |

Формат MAC и IP: [MAC_IP.md](MAC_IP.md). Сам протокол ARP: [ARP.md](ARP.md).

## 3. Кадр, а не пакет

На L2 единица передачи — **кадр** (frame). IP-**пакет** лежит внутри него как полезная нагрузка.

Ethernet II, то, что собирает ft_malcolm для ARP:

```
 0                   6                   12      14
┌───────────────────┬───────────────────┬───────┬──────────────┐
│ destination MAC   │ source MAC        │ type  │ payload      │
│ 6 байт            │ 6 байт            │ 2     │ ARP или IPv4 │
└───────────────────┴───────────────────┴───────┴──────────────┘
```

| EtherType | Внутри |
|-----------|--------|
| `0x0800` | IPv4-пакет |
| `0x0806` | ARP |
| `0x86DD` | IPv6 |

Минимальная длина кадра на проводе — 64 байта вместе с FCS (контрольной суммой, 4 байта). Без FCS это 60 байт. ARP полезной нагрузки занимает 42 байта (14 Ethernet + 28 ARP). Нехватку добивает padding. FCS считает сетевая карта. В `AF_PACKET` его обычно уже нет: программа видит заголовок и payload.

Source MAC в кадре — «кто отправил этот хоп». Destination — «кому на этом хопе». После роутера оба будут другими, даже если IP destination тот же. Это граница: L2 переписывается на каждом канале, L3 тянется до конца (пока нет NAT).

## 4. Кто соединяет хосты

| Устройство | Уровень | Как ведёт кадр |
|------------|---------|----------------|
| Кабель / veth | L1 | просто среда |
| Хаб | L1 | повторяет биты во все порты. Все слышат всех. Сейчас редок |
| Мост (bridge) | L2 | несколько портов, одна таблица MAC, один broadcast domain |
| Свитч | L2 | мост на много портов |
| Точка доступа Wi-Fi | L2 | клиенты одного BSS — как порты одного моста, если нет client isolation |
| Роутер | L3 | снимает Ethernet, смотрит IP, собирает новый кадр в другой сегмент |
| Хост с forwarding | L3 | то же, если включён `ip_forward` |

Домашний «роутер» — обычно три вещи в одной коробке: свитч на LAN-портах, точка доступа и роутер между LAN и провайдером. Порты LAN и Wi-Fi часто в **одном** L2. Порт WAN — уже другой сегмент.

Linux-мост (`br0`) делает то же, что свитч: интерфейсы, добавленные в мост, видят кадры друг друга. Так устроены многие виртуальные сети.

## 5. Таблица MAC на свитче

Свитч не рассылает каждый кадр всем. Он держит таблицу:

```
MAC                    порт
aa:77:fb:2e:e0:ed      1
aa:77:fb:2e:e0:aa      2
52:54:00:12:34:56      3
```

Как она наполняется:

1. Приходит кадр на порт 1, source MAC = `aa:bb:…`.
2. Свитч записывает: этот MAC живёт за портом 1.
3. Destination известен и сидит на порту 2 — кадр уходит только туда.
4. Destination неизвестен — кадр **flood**: копия во все порты VLAN, кроме входящего.
5. Destination = `ff:ff:ff:ff:ff:ff` — тоже во все порты. Это не ошибка обучения, это broadcast.

Запись живёт ограниченное время (часто 5 минут) и обновляется, когда с этого MAC снова приходит кадр. Выдернул кабель и воткнул в другой порт — пока старая запись не протухнет или не придёт новый кадр, свитч может слать не туда.

Эта таблица **не** ARP-кэш.

| | Таблица свитча (CAM) | ARP / neighbor на хосте |
|--|----------------------|-------------------------|
| Ключ | MAC | IP |
| Значение | порт | MAC |
| Кто заполняет | любой входящий кадр по source MAC | ARP Reply |
| Зачем | куда физически отдать кадр | какой MAC поставить в Ethernet dest |

ft_malcolm меняет вторую таблицу у жертвы. Свитч при этом честно доставляет кадры на тот MAC, который жертва теперь считает владельцем IP. Если этот MAC реально есть на сегменте (карта атакующего), кадры придут на её порт.

## 6. Unicast, broadcast, flooding

Три разных случая, их часто смешивают.

**Unicast.** Destination MAC — конкретная карта. Свитч, если уже выучил порт, шлёт кадр только туда. ARP Reply ft_malcolm такой: dest = `target_mac`.

**Broadcast.** Destination = `ff:ff:ff:ff:ff:ff`. Получают все интерфейсы сегмента. ARP Request такой. Ответить может каждый, кто пакет услышал. Фильтр в `arp_listen.c` как раз требует этот dest.

**Flooding.** Dest — обычный unicast, но свитч ещё не знает порт. Кадр временно уходит всем, как broadcast. Как только владелец MAC что-нибудь отправит, свитч выучит порт и flood прекратится.

Multicast (групповой MAC, нечётный первый октет) свитч тоже часто льёт шире, чем unicast. Для этого проекта достаточно broadcast и unicast.

Карта, которой кадр не адресован, в норме его отбрасывает ещё в железе. Чтобы видеть чужой unicast, нужен promiscuous mode. Broadcast и так попадает в систему: он адресован всем.

## 7. Широковещательный домен

**Broadcast domain** — множество интерфейсов, до которых доходит один broadcast-кадр.

Внутрь домена входят:

- все порты свитча в том же VLAN;
- интерфейсы, посаженные в один Linux-мост;
- Wi-Fi клиенты той же сети, если точка не изолирует их друг от друга.

Не входят:

- хосты за роутером;
- другой VLAN, даже на том же свитче;
- вторая VM в отдельном NAT, у которой свой виртуальный свитч.

Проверка «мы в одном L2» простая. На машине A:

```bash
arping -c 1 -I enp0s1 192.168.65.15
```

Ответ пришёл, в `ip neigh` появился MAC машины B — сегмент общий. `ping` при этом может проходить и через роутер, поэтому ping сам по себе доказательством не является. `arping` шлёт ARP и дальше своего L2 не уходит.

Размер домена — это и есть поверхность ARP. Кто слышит Request, тот может прислать Reply.

---

## 8. VLAN

**VLAN** (IEEE 802.1Q) режет один физический свитч на несколько широковещательных доменов.

Кадр между свитчами может нести тег: номер VLAN, 12 бит (1…4094). Порт доступа (access) отдаёт хосту кадр уже без тега и кладёт тег, когда кадр приходит от хоста. Для операционной системы на access-порте VLAN не виден: обычный Ethernet.

Хост в VLAN 10 не получает broadcast VLAN 20. ARP между ними не ходит, даже если оба кабеля воткнуты в один коммутатор. Маршрут между VLAN делает роутер (или L3-свитч) — и на каждом таком переходе Ethernet собирается заново.

Для лабы ft_malcolm обе VM должны оказаться в **одном** VLAN. Разные VLAN — как разные свитчи.

## 9. Где L2 кончается

Роутер принимает кадр, если destination MAC — его собственный (или broadcast, который он обрабатывает как хост). Дальше он смотрит IP. В соседнюю сеть уходит **новый** кадр:

```
сегмент жертвы                         сегмент за роутером
Ethernet dest = MAC роутера      →     Ethernet dest = MAC следующего хопа
Ethernet src  = MAC жертвы             Ethernet src  = MAC роутера
IP dest       = 8.8.8.8                IP dest       = 8.8.8.8
```

MAC жертвы в правом сегменте никто не видит. Поддельный ARP Reply, посланный слева, справа не существует.

Поэтому:

- spoofing шлюза влияет на то, куда жертва шлёт кадры **внутри своей LAN**;
- хост в интернете по MAC жертвы не адресуется и её ARP-таблицу не видит;
- две VM «с интернетом» ещё не в одном сегменте, если у каждой свой NAT.

`ip route` показывает, какой next hop L3. L2 для этого next hop — отдельная строка в `ip neigh`.

## 10. Wi-Fi

Для IP Wi-Fi выглядит как Ethernet: те же MAC, тот же ARP, тот же EtherType. Общая среда — радио одной точки доступа (BSS), а не кабель.

Отличия, которые ломают лабу:

| Свойство | Эффект |
|----------|--------|
| Client isolation / AP isolation | точка не мостит кадры между клиентами. Они видят только шлюз. ARP соседа не дойдёт |
| Мост UTM/VirtualBox через Wi-Fi | точка часто не принимает кадр с чужим source MAC. Bridged-режим «через Wi-Fi» молчит |
| Один SSID, разные VLAN | гостиница и гостевая сеть: клиенты не в одном L2, хотя имя сети похоже |

Надёжнее сажать обе VM в виртуальный сегмент на хосте, а не надеяться на общий Wi-Fi.

## 11. Виртуальные машины

Гипервизор подставляет виртуальный свитч. Режим сети решает, один это L2 или несколько.

| Режим в UTM | Что получается |
|-------------|----------------|
| **Shared Network** | гости QEMU часто попадают в одну сеть с хостом и друг с другом. Для двух VM под ARP это первый кандидат |
| **Bridged** | порт VM как будто воткнут в физический интерфейс Mac. Обе VM на одном интерфейсе видят и друг друга, и реальную LAN. На Wi-Fi часто не работает |
| **Emulated VLAN** | у каждой VM **свой** сегмент. Друг друга они не слышат |
| NAT «у каждой свой» | то же: два разных L2, общий только выход в интернет |

Нужная схема для проекта:

```
VM1 (атакующий)                         виртуальный свитч                         VM2 (жертва)
enp0s1 192.168.65.14  aa:77:fb:2e:e0:ed    ←── один broadcast domain ──→    enp0s1 192.168.65.15  aa:77:fb:2e:e0:aa
```

Проверка с обеих сторон: `ip addr` показывает `192.168.65.0/24`, `arping` на IP соседа отвечает его MAC.

Обе машины в одной сети `/24`, on-link, без роутера посередине.

## 12. Почему здесь работает ft_malcolm

Программа открывает `AF_PACKET` на одном интерфейсе и видит Ethernet-кадры этого сегмента.

1. Жертва шлёт ARP Request. Destination MAC — broadcast, поэтому кадр доходит до каждого порта сегмента, включая атакующего.
2. Ответ — unicast на `target_mac`. Свитч доставляет его на порт жертвы.
3. Жертва записывает в neighbor: `source_ip → source_mac`.
4. Следующие IP-пакеты жертвы к этому IP получают Ethernet dest = поддельный MAC. Свитч несёт их туда, где этот MAC выучен.

Всё это обрывается на роутере. Другой VLAN, другой NAT, client isolation — Request не приходит, и фильтр в `listen_arp_request` никогда не срабатывает. Сокет при этом открыт, программа просто молчит.

Успех выглядит так: на жертве `ip neigh` показывает MAC из аргумента `source_mac`, а `tcpdump -e` на атакующем видел и broadcast Request, и unicast Reply.

## 13. Команды

```bash
ip link show                    # интерфейсы, MAC, в каком они состоянии
bridge link                     # кто добавлен в мост, если он есть
bridge fdb show                 # таблица MAC моста (аналог CAM свитча)

ip addr show
ip neigh show
arping -c 1 -I enp0s1 192.168.65.15   # сосед в этом L2 или нет

sudo tcpdump -i enp0s1 -n -e arp  # broadcast Request и unicast Reply
```

В выводе `tcpdump -e` поле до протокола — пара MAC. Broadcast выглядит как `ff:ff:ff:ff:ff:ff`. Если Request жертвы на этом интерфейсе не появляется, машины не в одном сегменте. Дальше смотреть аргументы программы смысла нет.

# NIC и кадр

Сетевая карта принимает и отдаёт кадры. Кадр — это то, что реально идёт по проводу. IP-пакет лежит внутри. ft_malcolm не пользуется IP-стеком: он открывает одну карту и сам кладёт байты кадра.

## 1. NIC

**NIC** (Network Interface Card) — сетевая карта, контроллер, через который хост выходит на линк. Это может быть отдельная плата, чип на материнской плате, Wi-Fi-адаптер или полностью программное устройство в виртуалке.

Карта — граница между операционной системой и средой:

```
приложение
    │
  ядро: сокеты, IP, ARP-кэш
    │
  драйвер NIC
    │
  карта: MAC, очередь кадров, FCS
    │
  кабель / радио / виртуальный провод
```

У карты есть свой **MAC**. Когда в кадре destination совпадает с этим MAC, с broadcast или с группой, на которую карта подписана, кадр забирают наверх. Чужой unicast карта обычно выбрасывает ещё в железе.

Имена одного и того же предмета:

| Слово | Где встречается |
|-------|-----------------|
| NIC, адаптер, сетевая карта | железо или его эмуляция |
| интерфейс | объект ядра: `enp0s1`, `eth0`, `wlan0` |
| link | состояние линка: поднят, есть несущая |
| iface | то же интерфейс, так поле названо в `t_malcolm` |

Один физический разъём — обычно один интерфейс. Несколько IP могут висеть на одном интерфейсе. Несколько интерфейсов — несколько MAC и несколько линков.

Формат самого MAC: [MAC_IP.md](MAC_IP.md). Куда карта воткнута в сегмент: [L2_L3.md](L2_L3.md).

## 2. Интерфейс в системе

Ядро показывает карту как сетевой интерфейс. У него есть имя, индекс, флаги и адреса.

```bash
ip link show
```

Типичная строка:

```
2: enp0s1: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP
    link/ether aa:77:fb:2e:e0:ed brd ff:ff:ff:ff:ff:ff
    inet 192.168.65.14/24 brd 192.168.65.255 scope global dynamic enp0s1
```

| Поле | Смысл |
|------|--------|
| `2` | индекс интерфейса, `ifindex`. Его `sendto` кладёт в `sockaddr_ll` |
| `enp0s1` | имя. Его требует `SO_BINDTODEVICE` и `-i` |
| `UP` | административно включён |
| `LOWER_UP` | на проводе есть несущая: кабель воткнут, виртуальный линк поднят |
| `BROADCAST` | интерфейс умеет широковещательный адрес |
| `MULTICAST` | умеет групповые MAC |
| `LOOPBACK` | это `lo`, не выход в сегмент |
| `mtu 1500` | максимум полезной нагрузки IP в одном кадре |
| `link/ether …` | MAC, с которым карта сейчас работает |
| `brd ff:ff:ff:ff:ff:ff` | Ethernet-broadcast для этого линка |

`lo` тоже интерфейс, но кадры с него никуда не уходят. ft_malcolm при автовыборе его пропускает: нужен `AF_INET`, флаг `UP` и отсутствие `IFF_LOOPBACK`.

Индекс и имя — не одно и то же. Имя можно переименовать, индекс ядро выдаёт само и использует в пакетных сокетах. `getifaddrs` отдаёт и IPv4-адрес интерфейса, и отдельную запись `AF_PACKET` с MAC и `sll_ifindex`.

## 3. Что карта делает с кадром

На передаче драйвер отдаёт карте байты, начиная с destination MAC. Карта перед проводом добавляет то, чего в сокете уже нет.

**Передача:**

1. Драйвер складывает кадр в очередь карты.
2. Если длина меньше минимума Ethernet, карту дополняют padding'ом.
3. Карта считает **FCS** (Frame Check Sequence), 4 байта CRC, и дописывает в конец.
4. На провод уходят преамбула и признак начала кадра, затем сам кадр. Преамбула нужна, чтобы приёмник поймал тактировку. В операционной системе её не видно.
5. После успешной отправки буфер освобождают.

**Приём:**

1. Карта синхронизируется по преамбуле и отрезает её.
2. Проверяет FCS. Битный мусор на кабеле отбрасывается здесь, до ядра.
3. Смотрит destination MAC. Не наш unicast — кадр выброшен, если не включён promiscuous mode.
4. Драйвер отдаёт ядру кадр **без** преамбулы и обычно без FCS: destination MAC, source MAC, EtherType, payload.

Поэтому программа, читающая `AF_PACKET`, видит не «всё, что было на меди», а кадр в том виде, в каком его отдал драйвер. Разница с отправленными 42 байтами ARP — как раз padding и иногда хвост, который драйвер не срезал.

## 4. Какие кадры карта пускает наверх

По умолчанию наверх идут:

| Destination MAC | Попадает в систему |
|-----------------|--------------------|
| равен MAC этой карты | да |
| `ff:ff:ff:ff:ff:ff` | да, это broadcast |
| групповой MAC, на который интерфейс подписан | да |
| чужой unicast | нет |

ARP Request — broadcast, его увидит каждая карта сегмента без специальных режимов. ARP Reply ft_malcolm — unicast на MAC жертвы, его примет карта жертвы и не примут остальные.

**Promiscuous mode** снимает фильтр: карта отдаёт и чужие unicast. Так работает `tcpdump`, когда его запустили на интерфейсе. Для приёма broadcast Request этот режим не нужен. ft_malcolm его не включает: сокет `ETH_P_ARP` и так получает ARP-кадры, которые карта не отфильтровала.

На свитче чужой unicast до твоей карты часто даже не доходит: свитч шлёт его в другой порт. Promiscuous на хосте не заменяет положение в сегменте. Подробнее про порты и flood: [L2_L3.md](L2_L3.md).

## 5. Виртуальная карта

В виртуальной машине PCI-устройства Ethernet может не быть. Гипервизор даёт **virtio-net** или аналог: для гостя это обычный интерфейс с MAC, очередями и именем `enp0s1`. Кадр уходит не в кабель, а в виртуальный свитч.

Для ядра гостя разницы почти нет:

- есть имя, индекс, MAC, MTU, флаги `UP` / `LOWER_UP`;
- `AF_PACKET` читает и пишет те же Ethernet-заголовки;
- соседняя VM получит кадр, только если виртуальный свитч сидит с ней в одном сегменте.

`veth` — пара виртуальных концов одного провода внутри одного ядра: что записали в один, выходит из другого. Им пользуются контейнеры и мосты. Для двух VM это уже не `veth`, а сеть гипервизора, но кадр тот же.

MAC виртуальной карты задаёт гипервизор. Его видно в `ip link`. Поддельный MAC в аргументе ft_malcolm — не MAC этой карты. Это байты, которые программа запишет в заголовок кадра. Карта их отправит, даже если source в кадре не совпадает с её собственным адресом. Свитч выучит тот source, который стоит в кадре.

## 6. Что такое кадр

**Кадр** (frame) — порция данных канального уровня: заголовок L2, полезная нагрузка и служебные байты, которые понимает соседняя карта.

Рядом живут другие слова. Это не синонимы.

| Слово | Уровень | Пример |
|-------|---------|--------|
| кадр, frame | L2 | Ethernet-кадр с MAC и EtherType |
| пакет, packet | L3 | IPv4-пакет с адресами `192.168.65.14` → `192.168.65.15` |
| сегмент, datagram | L4 | TCP-сегмент или UDP-датаграмма внутри IP |
| поток битов | L1 | то, что на кабеле, включая преамбулу |

Вложение:

```
кадр Ethernet
└── пакет IPv4          EtherType 0x0800
    └── сегмент TCP
        └── байты приложения

кадр Ethernet
└── сообщение ARP       EtherType 0x0806
```

ARP — не IP-пакет. Это отдельная полезная нагрузка кадра. У неё свой заголовок на 28 байт и нет TTL, портов и IP-маршрута.

Говорить «ARP-пакет» привычно, и в коде структура называется `t_arp_packet`. На проводе это кадр: первые 14 байт — Ethernet, без них свитч и чужая карта содержимое не доставят.

Кадр живёт один хоп. Роутер кадр разбирает, пакет (если это IP) маршрутизирует и собирает новый кадр уже с другими MAC. До получателя в другой подсети доезжает пакет, не исходный кадр.

## 7. Из чего состоит Ethernet-кадр

На проводе кадр длиннее, чем буфер в программе.

```
преамбула 7 байт     карта, в ОС не видна
SFD       1 байт     «начало кадра», в ОС не видно
┌ destination MAC  6
│ source MAC       6
│ EtherType        2
│ payload          46…1500 у обычного Ethernet
│ padding          если payload короче 46
└ FCS              4 байта CRC, считает карта
```

То, что видно в `AF_PACKET` и в `tcpdump`:

```
Offset  Size  Поле              ARP в ft_malcolm
0       6     destination MAC   broadcast или MAC жертвы
6       6     source MAC        source_mac из аргументов
12      2     EtherType         0x0806
14      …     payload           28 байт ARP
```

**EtherType** говорит, как читать payload.

| Значение | Содержимое |
|----------|------------|
| `0x0800` | IPv4 |
| `0x0806` | ARP |
| `0x86DD` | IPv6 |
| `0x8100` | тег VLAN 802.1Q; настоящий EtherType стоит на 4 байта дальше |

Поля destination и source — про этот хоп. Кто конечный хозяин IP, из них не следует: это написано либо в IP-заголовке внутри, либо в полях ARP sender/target.

Один кадр — одна передача. ARP Request и ARP Reply — два разных кадра. Ответ не «дописывается» в запрос.

## 8. Длина, padding и MTU

Классический Ethernet требует кадр не короче 64 байт **с FCS**. Без FCS это 60 байт от destination MAC до конца padding. Заголовок Ethernet II — 14 байт, значит payload вместе с padding не короче 46 байт.

ARP payload — 28 байт. До 46 не хватает 18. Их дописывают нулями.

| Кто собрал | Сколько байт |
|------------|----------------|
| ft_malcolm в `sendto` | 42: 14 Ethernet + 28 ARP, без padding и без FCS |
| драйвер / карта на проводе | 60 + 4 FCS |
| `recvfrom` у соседа | часто 42, иногда 60, если padding не срезали |

Поэтому приём сравнивает длину с минимумом `sizeof(t_arp_packet)`, а не с точным равенством. Лишние байты в конце на разбор ARP не влияют: поля лежат в первых 42.

**MTU** — верхняя граница payload, не всего кадра. `mtu 1500` значит: в кадр влезает 1500 байт после Ethernet-заголовка (для IP — сам IP-пакет). ARP в эту границу упирается никогда. Если IP-пакет больше MTU, его режут на несколько кадров (фрагментация) или соединение договаривается о меньшем размере (TCP MSS). К одному ARP-кадру это отношения не имеет.

Jumbo-кадры (MTU 9000) и кадры с VLAN-тегом меняют смещения и минимум длины. В этом проекте кадр всегда без тега: EtherType сразу в байтах 12–13.

## 9. Кадр в ft_malcolm

Программа выбирает одну карту и привязывает к ней raw-сокет.

```
find_interface()
  имя: первый UP не-lo с IPv4, либо -i
  из записи AF_PACKET: MAC карты и ifindex

open_raw_socket()
  socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ARP))
  SO_BINDTODEVICE = имя
```

`SOCK_RAW` здесь значит: в буфере есть Ethernet-заголовок, ядро его не отрезает. `ETH_P_ARP` значит: в сокет попадают кадры с EtherType `0x0806`, а не весь трафик карты.

Дальше два направления.

**Приём.** `recvfrom` пишет в буфер байты кадра. Указатель приводят к `t_arp_packet *`, потому что структура packed и совпадает с первыми 42 байтами. Фильтр смотрит destination MAC, opcode и IP внутри ARP. Чужой EtherType до этого кода не доходит: его отсёк сам сокет.

**Передача.** `send_arp_reply` заполняет те же 42 байта и вызывает `sendto`. В `sockaddr_ll` стоят `ifindex` карты и destination MAC. Карта, а не программа, добавит padding и FCS.

Свой MAC интерфейса (`iface_mac`) в заголовок Reply не подставляется. В source кадра пишется `source_mac` из аргументов. Карта этот кадр всё равно отправляет: она не обязана требовать, чтобы source совпадал с адресом, прошитым в ней.

Итог на проводе — обычный Ethernet-кадр соседней карты. Жертва не отличает его от кадра, который собрал бы её настоящий сосед, кроме значения MAC в полях sender.

Разбор полей ARP внутри payload: [ARP.md](ARP.md). Порядок вызовов: [HOW_IT_WORKS.md](HOW_IT_WORKS.md).

## 10. Команды

```bash
ip link show                         # имя, индекс, MAC, UP, MTU
ip -s link show enp0s1               # плюс счётчики отправленных и принятых кадров
ethtool enp0s1                       # скорость, дуплекс, есть ли несущая
ethtool -S enp0s1                    # счётчики самой карты, если драйвер их отдаёт

sudo tcpdump -i enp0s1 -n -e -XX arp # кадр: MAC, EtherType, hex
```

В `tcpdump -e` первая часть строки до типа протокола — заголовок кадра. `length 42` или `length 60` — сколько байт отдал драйвер, без преамбулы. FCS в этой цифре обычно нет.

Если интерфейс есть, но `state DOWN` или нет `LOWER_UP`, карта кадры в сегмент не отдаёт. Сначала линк, потом ARP.

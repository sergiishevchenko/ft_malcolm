# MAC и IP-адрес

Два адреса, без которых не читается ни Ethernet-кадр, ни аргументы ft_malcolm. MAC доставляет кадр по проводу. IPv4 говорит, какому хосту предназначен пакет. ARP связывает их в одной локальной сети.

## 1. Зачем два адреса

Приложение знает соседа по имени или по IP: `10.0.2.20`. Сетевая карта этого не понимает. Она передаёт кадр на 48-битный адрес, прошитый (или назначенный) интерфейсу, — **MAC**.

| | MAC | IPv4 |
|--|-----|------|
| Слой | L2, Ethernet | L3, сеть |
| Длина | 48 бит, 6 байт | 32 бита, 4 байта |
| Область | один L2-сегмент (свитч, VLAN, Wi-Fi) | может идти через роутеры |
| Кто смотрит | NIC и свитч | IP-стек хоста и роутер |
| Пример | `08:00:27:dd:ee:ff` | `10.0.2.20` |
| Меняется в пути | на каждом хопе | адрес назначения пакета остаётся, пока пакет не дошёл |

IP отвечает на вопрос «какой хост». MAC — «какая сетевая карта на этом куске провода прямо сейчас».

Без MAC кадр некому отдать на Ethernet. Без IP хост в другой подсети не адресовать: MAC за роутером не виден.

## 2. Где они лежат в кадре

Обычный IPv4-кадр по Ethernet несёт **оба** адреса. Они в разных заголовках и решают разные задачи.

```
Ethernet II                         IPv4
┌──────────────────────────┐        ┌──────────────────────────┐
│ dest MAC   6 байт        │        │ dest IP    4 байта       │
│ src  MAC   6 байт        │        │ src  IP    4 байта       │
│ EtherType  0x0800        │        │ протокол, TTL, …         │
└──────────────────────────┘        └──────────────────────────┘
        доставка кадра                    логический адресат
        только до следующего L2-хопа     сохраняется end-to-end
```

ARP — отдельный EtherType `0x0806`. Внутри него снова две пары: sender/target MAC и sender/target IP. Это не IP-пакет. Это вопрос «какой MAC у этого IP?» и ответ на него.

Подробный разбор ARP-кадра: [ARP.md](ARP.md).

## 3. MAC-адрес

**MAC** (Media Access Control), он же hardware address, physical address, Ethernet address. 48 бит. Пишут шестью шестнадцатеричными байтами.

```
08:00:27:dd:ee:ff
│  │  │  │  │  └─ 6-й октет
│  │  └────────── 3-й октет
└──┴───────────── первые 3 октета: OUI (производитель / блок адресов)
```

Регистр не важен: `AA:BB:CC:DD:EE:FF` и `aa:bb:cc:dd:ee:ff` — один адрес. Разделители в дикой природе бывают `:`, `-` и иногда `.` (`aabb.ccdd.eeff` у Cisco). ft_malcolm принимает только `XX:XX:XX:XX:XX:XX`, ровно 17 символов.

На проводе это шесть байт без двоеточий:

```
08 00 27 dd ee ff
```

### Биты первого октета

Первый байт читают от старшего бита. Два младших бита этого байта — флаги (в том порядке, в каком они передаются по проводу: I/G, затем U/L).

| Бит | Имя | 0 | 1 |
|-----|-----|---|---|
| младший бит 1-го октета (I/G) | Individual / Group | unicast, одна карта | multicast, группа |
| следующий бит (U/L) | Universal / Local | адрес из блока IEEE (OUI) | адрес назначен локально, не глобально уникален |

Проверка на глаз по первому байту:

| Первый байт | Что это |
|-------------|---------|
| чётный (`08`, `52`, `de`, `aa`) | unicast |
| нечётный (`01`, `33`, `ff`) | multicast или broadcast |
| `ff` | broadcast, если весь адрес `ff:ff:ff:ff:ff:ff` |

`ff:ff:ff:ff:ff:ff` — широковещательный MAC. Кадр с таким destination получают все в сегменте. ARP Request едет именно так.

Multicast MAC для IPv4 строится из IP: `01:00:5e` плюс младшие 23 бита группового IP. Для ft_malcolm это не нужно: программа различает только unicast жертвы и broadcast.

### OUI

Первые 24 бита у глобально уникального адреса — **OUI** (Organizationally Unique Identifier), блок, выданный IEEE производителю. Остальные 24 бита производитель назначает сам.

Узнаваемые префиксы в лабе:

| Префикс | Откуда часто |
|---------|----------------|
| `08:00:27` | VirtualBox |
| `52:54:00` | QEMU |
| `00:0c:29` / `00:50:56` | VMware |
| `de:ad:be` | локально выдуманный (бит U/L взведён у `de`) |

`de:ad:be:ef:00:01` в примерах ft_malcolm — не «адрес производителя». Это произвольный unicast, который мы подсовываем в ARP. Бит local у `0xde` взведён: такой MAC законно ставить вручную, он не претендует на глобальную уникальность.

### Где MAC живёт

- На карте: заводской адрес (BIA, burned-in). ОС может подменить его в драйвере — для сети важен тот, что сейчас на интерфейсе, не тот, что в EEPROM.
- В кадре: Ethernet source и destination.
- На свитче: таблица MAC → порт (CAM). Свитч учит source MAC входящих кадров и по dest решает, в какой порт слать. Broadcast уходит во все порты VLAN.
- В ARP-кэше хоста: как значение по ключу IP. Хост сам MAC соседа не «вычисляет», он его узнаёт.

Свой MAC и IP смотрят так:

```bash
ip link show          # MAC у link/ether
ip addr show          # IPv4 у inet
```

## 4. IPv4-адрес

32 бита. Обычная запись — четыре десятичных октета `0..255`:

```
10.0.2.20
```

На проводе — четыре байта, старший октет первым (network byte order):

```
0a 00 02 14
```

Тот же адрес одним числом (так принимает бонус ft_malcolm):

```
10.0.2.20 = (10 << 24) + (0 << 16) + (2 << 8) + 20 = 167772692
```

`inet_pton` разбирает dotted-decimal. Строка из одних цифр в `validate_ip` режется на 4 октета сдвигом. Hostname через `getaddrinfo` даёт те же 4 байта.

### Что IP не говорит

IP не говорит, в какой порт свитча воткнуть кабель и какой MAC у получателя. Он говорит, в какую сеть и какому хосту внутри логической схемы адресован пакет.

Один хост может иметь несколько IP (несколько интерфейсов, алиасы). Один IP в норме не должен быть у двух машин сразу: это конфликт, его ловит gratuitous ARP / RFC 5227.

## 5. Маска, сеть и хост

IP сам по себе не делится на «сеть» и «хост». Делит **маска**.

`10.0.2.20/24` значит: первые 24 бита — номер сети, последние 8 — номер хоста.

```
адрес    00001010.00000000.00000010.00010100   10.0.2.20
маска    11111111.11111111.11111111.00000000   255.255.255.0
сеть     00001010.00000000.00000010.00000000   10.0.2.0
хост                              .00010100   .20
```

| Запись | Смысл |
|--------|--------|
| `/8` | маска `255.0.0.0`, 16 млн адресов в сети |
| `/16` | `255.255.0.0` |
| `/24` | `255.255.255.0`, 256 адресов, типичная домашняя и лабораторная сеть |
| `/32` | один адрес, «этот хост», маска из всех единиц |

В сети `/24` крайние адреса служебные:

| Адрес | Роль |
|-------|------|
| `10.0.2.0` | номер сети, не назначают хосту |
| `10.0.2.1` … `10.0.2.254` | хосты |
| `10.0.2.255` | directed broadcast этой сети |

Два хоста в одной сети (совпали биты под маской) считаются соседями по L2: ядро шлёт кадр **прямо на MAC этого IP**. Если сети разные — кадр идёт на **MAC шлюза**, а IP назначения внутри пакета остаётся чужим. Это место, где путают ARP: ping `8.8.8.8` порождает ARP не на `8.8.8.8`, а на default gateway.

Старые классы A/B/C (`/8`, `/16`, `/24` по первому октету) больше не используются для маршрутизации. Живёт CIDR: длина префикса задаётся явно.

## 6. Особые IP

| Адрес | Что значит |
|-------|------------|
| `0.0.0.0` | «адреса ещё нет». В ARP Probe (RFC 5227) так ставится sender IP |
| `127.0.0.0/8` | loopback. `127.0.0.1` — этот же хост, пакет не выходит на провод |
| `255.255.255.255` | limited broadcast: все на этом сегменте. Роутер дальше не пересылает |
| `10.0.0.0/8` | частная сеть, RFC 1918 |
| `172.16.0.0/12` | частная (`172.16.0.0`–`172.31.255.255`) |
| `192.168.0.0/16` | частная |
| `169.254.0.0/16` | link-local, если DHCP не выдал адрес |
| `224.0.0.0/4` | multicast |
| `240.0.0.0/4` | зарезервировано, в обычной практике не используется |

Частные адреса не маршрутизируются в интернете. Домашний роутер делает NAT: снаружи виден один публичный IP, внутри — `192.168.x.x`. Для ft_malcolm это важно так: атака живёт **внутри** одной L2-сети. Частный или публичный IP жертвы не меняет механику, если оба хоста в одном сегменте.

`localhost` резолвится в `127.0.0.1`. Для проверки spoofing между двумя VM он бесполезен: кадр не уйдёт соседу.

## 7. Как пакет использует оба адреса

Хост A `10.0.2.10` / `08:00:27:aa:bb:cc` шлёт ping хосту B `10.0.2.20` / `08:00:27:dd:ee:ff`. Маска `/24`, шлюз `10.0.2.1`.

A смотрит маску: `10.0.2.20` в той же сети. Next hop — сам B. В ARP-кэше нет записи → ARP Request (broadcast MAC, target IP = `10.0.2.20`). Приходит Reply. Дальше кадр:

```
Ethernet dest = 08:00:27:dd:ee:ff     MAC B
Ethernet src  = 08:00:27:aa:bb:cc     MAC A
EtherType     = 0x0800                IPv4

IP dest = 10.0.2.20
IP src  = 10.0.2.10
```

Оба адреса указывают на B, потому что B — сосед.

Теперь A пингует `8.8.8.8`. Это другая сеть. Next hop — шлюз `10.0.2.1`, допустим MAC `52:54:00:12:34:56`.

```
Ethernet dest = 52:54:00:12:34:56     MAC шлюза, не 8.8.8.8
Ethernet src  = 08:00:27:aa:bb:cc

IP dest = 8.8.8.8                     конечный адресат не меняется
IP src  = 10.0.2.10
```

Свитч смотрит только на Ethernet dest. Роутер снимет Ethernet, прочитает IP dest и соберёт **новый** Ethernet уже в сторону своего next hop.

## 8. Что меняется на роутере

На каждом L3-хопе:

| Поле | Поведение |
|------|-----------|
| IP source / dest | остаются (NAT — отдельный случай, он переписывает IP) |
| TTL | уменьшается на 1 |
| Ethernet src | становится MAC исходящего интерфейса роутера |
| Ethernet dest | становится MAC следующего хопа |
| ARP | роутер резолвит MAC next hop в **своей** сети, не MAC исходного отправителя |

Поэтому MAC жертвы из другой подсети с вашей VM не виден и в ARP-ответ не подставляется. ft_malcolm работает только там, где оба MAC живут в одном широковещательном домене.

Обратное тоже верно: подмена MAC в ARP-кэше жертвы меняет только L2 next hop для этого IP. IP-адрес в пакетах жертвы остаётся тем, что она и так хотела. Меняется карта, на которую свитч доставит кадр.

## 9. Как это выглядит в ft_malcolm

Четыре аргумента — две пары «IP + MAC»:

```
sudo ./ft_malcolm <source_ip> <source_mac> <target_ip> <target_mac>
```

| Аргумент | Адрес | Куда попадает в Reply |
|----------|--------|------------------------|
| `source_ip` | IPv4, который врём | ARP sender IP. Это ключ, который жертва запишет в кэш |
| `source_mac` | MAC, который подставляем | ARP sender MAC и Ethernet source |
| `target_ip` | IPv4 жертвы | ARP target IP. Фильтр входящего Request сравнивает его с sender IP запроса |
| `target_mac` | реальный MAC жертвы | Ethernet dest и ARP target MAC. Сюда уходит unicast |

Программа не спрашивает маску и не проверяет, что оба IP в одной подсети. Если они в разных L2, Request жертвы до сокета просто не дойдёт.

Валидация:

- IP: `a.b.c.d`, либо десятичное 32-битное число, либо hostname → 4 байта;
- MAC: `XX:XX:XX:XX:XX:XX` → 6 байт. Broadcast `ff:ff:ff:ff:ff:ff` как *формат* пройдёт, но как `target_mac` он превратит Reply в broadcast.

После удачного Reply кэш жертвы содержит строку вида:

```
10.0.2.10 lladdr de:ad:be:ef:00:01 REACHABLE
```

Слева IP, справа MAC. Вся работа программы — сделать правую часть ложной.

## 10. Команды

```bash
ip link show                         # MAC интерфейсов
ip addr show                         # IPv4, маска, broadcast
ip route show                        # кто шлюз и какие сети on-link

ip neigh show                        # кэш IP → MAC
arp -a                               # то же, старый вывод

# разовый запрос MAC для IP
arping -c 1 -I eth0 10.0.2.10

# кадр целиком: Ethernet MAC и, если это IPv4, IP
sudo tcpdump -i eth0 -n -e
```

В `tcpdump -e` сначала MAC (`src > dst`), потом протокол. Для ARP строка будет `Who has <IP>? Tell <IP>` и `is-at <MAC>`. Для ping — `IP <src-ip> > <dst-ip>`.
